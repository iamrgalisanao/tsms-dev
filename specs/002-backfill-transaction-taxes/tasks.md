Harmless today (nothing reads `$run`'s counters after `apply()` returns), but whoever wires `--apply` into the CLI and reports these counters (mirroring Slice 4's `buildResult()`) MUST either call `$run->refresh()` unconditionally after `apply()` returns, or re-fetch the run fresh before reporting — do not trust the returned object's in-memory counter values directly.

Inert today given this feature's synchronous, single-process design (no concurrent `apply()` invocations expected), but the "zero linked rows" invariant this whole feature depends on is enforced by a time-of-check, not time-of-insert, guarantee. Worth a unique constraint if this ever runs concurrently or gets queued.
  - **Noted at Slice 6 deadlock-retry fix's drift revalidation (2026-08-11)**: a cumulative mutation-path review found and fixed a bug where `processTransactionForApply()` nested an explicit `DB::transaction()` inside `DeadlockRetryService::withDeadlockRetry()`'s closure, which caused real deadlocks to bypass the retry entirely (Laravel throws a `DeadlockException`, not a `QueryException`, when a concurrency error occurs at transaction-depth > 1 — `withDeadlockRetry()`'s `catch (QueryException $e)` can't see it). The identical nested pattern still exists, unfixed, in the live `app/Services/TransactionIngestService.php::ingest()` (~line 55-56) — out of scope for this feature, tracked separately, but likely has the same defect in production.

- **Repo-wide test-infrastructure defect: `tests/TestCase.php:38` breaks `RefreshDatabase` transaction isolation.** Found during Slice 3 (2026-08-11), confirmed against the Laravel framework source (not just observed behavior): `setUp()` calls `$this->refreshApplication()` immediately after `parent::setUp()`, which is where `RefreshDatabase` opens its per-test transaction. `refreshApplication()` rebuilds the app container and DB connection, orphaning that transaction — so writes made during a test are never rolled back, and rows can leak between test methods within the same run. **Explicitly out of scope for this branch/feature** (per architecture direction, 2026-08-11) — this is a pre-existing, repo-wide defect unrelated to tax backfill, not something to fix as a side effect of this feature's slices. Needs its own follow-up ticket to fix `TestCase.php` and audit for count-sensitive tests elsewhere that aren't similarly scoped.
- **Likely repo-wide production defect: `TransactionIngestService::ingest()` (~line 55-56) probably has the same nested-transaction bug just fixed in this feature's `TaxBackfillRunner::apply()`.** Found 2026-08-11 during a cumulative mutation-path review of Slice 6. Confirmed against Laravel's actual source (`ManagesTransactions::handleTransactionException()`, `DeadlockException extends PDOException` not `QueryException`) that this nesting causes real deadlocks/lock-waits to bypass `DeadlockRetryService`'s retry logic entirely — the exact failure mode `DeadlockRetryService` exists to protect against on this same `transactions` table (see `research.md` R9 and the 2026-08-10 incident it documents). **Not touched or fixed as part of this feature** — it's live production code on the POS transaction-ingestion path, explicitly requiring the user's own separate authorization and testing before any change, not a drive-by fix alongside a backfill branch. If confirmed, the practical impact is that lock contention during live ingestion currently fails permanently on the first hit instead of retrying, silently reducing the resilience this service was built to provide. Recommend independent, prioritized investigation outside this feature's timeline.
